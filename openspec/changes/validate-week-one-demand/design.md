## Context

仓库当前只有协作规范与八周计划，没有应用代码、数据存储或部署基础设施。参见 `proposal.md` 的动机；本变更要同时交付可执行的研究资产、人工分析契约和最小获客入口，但不得因此提前搭建第二周的完整产品架构。

第一周会接触潜在客户信息和授权反馈样本，设计必须把“可提交的模板与脱敏证据”和“受控的身份信息与原始文件”分开。研究数量、报告统计和周验收需要确定性复算，语言模型只可辅助命名与表达。

## Goals / Non-Goals

**Goals:**

- 让访谈、样本接收、人工分析和周验收使用同一套可审计标识与模板。
- 在不提交真实客户身份信息和原始反馈的前提下，保留足以验证结论的脱敏证据链。
- 以无框架、低依赖的静态页面验证定位和登记转化，并为后续替换成正式 Web 应用保留边界。
- 用自动检查辅助验证数量门槛、必填字段和报告证据引用，而不是依赖口头汇报。

**Non-Goals:**

- 不建立正式账户、工作空间、项目、数据库、对象存储或异步任务。
- 不在本周实现自动脱敏、Embedding、聚类、模型调用或发布前后比较。
- 不在公开表单接收反馈文件，也不接入营销分析、广告追踪或复杂 CRM。
- 不把访谈完成数、样本数或重复意愿写成伪造的演示数据来满足验收。

## Decisions

### 1. 研究资产与真实数据分层存放

仓库新增 `validation/week-1/`，保存访谈指南、记录模板、样本登记模板、统一字段契约、分类 V1、Top 3 报告模板和周验收模板。真实联系方式与原始样本保存在操作者选定的仓库外受控位置；仓库内只允许不可识别身份的研究 ID、批次 ID、脱敏记录和汇总结果。

提交前通过 `.gitignore` 排除约定的本地私有目录，并提供隐私检查清单。相比把全部研究记录放进在线数据库，这种方式更适合尚未验证需求的第一周，也避免提前建设权限系统；代价是协作和审计主要依赖模板纪律。

### 2. 统一字段先最小化，未知值显式保留

反馈契约的最小必填字段为 `feedback_id`、`import_batch_id` 和 `content_redacted`。`occurred_at`、`product_version`、`channel`、`customer_ref`、`cohort`、`category`、`severity` 等字段允许为空，但必须显式标注未知，不得从上下文猜测。

问题分类 V1 使用少量互斥性要求较低的业务类别：功能缺口/请求、缺陷/阻断、易用性/流程摩擦、性能/可靠性、集成/兼容、计费/价格、上手/文档、支持/服务、其他/不确定。一条反馈可对应多个问题实例，每个实例仍引用同一个反馈 ID。相比一开始设计深层分类树，扁平多标签更容易在三份真实样本上发现边界问题并修订。

### 3. Top 3 使用透明工作表，不让模型生成统计

报告沿用项目计划中的 `frequency × severity × growth × confidence × segment_weight`。频次来自去重反馈 ID 数；严重度使用有定义的四档映射；增长只在存在可比较窗口时计算，否则明确标为“未测量”并取中性值 1；置信度记录样本量、证据完整度和归类一致性；用户群权重默认 1，只有事先声明的目标群体才可调整。

排序由工作表或标准库校验脚本复算。研究者可以人工调整最终顺序，但必须保留原分数、调整理由、正反证据 ID 和不确定性。相比完全主观选题，这保留可解释性；相比现在实现完整评分引擎，它足以验证规则是否能支持真实评审。

### 4. 用标准库校验器生成周验收摘要

实现一个不引入第三方依赖的校验命令，读取脱敏后的访谈清单、样本登记和报告元数据，检查必填字段、唯一 ID、授权状态、报告数量、证据引用和验收门槛。命令输出结构化结果和人类可读摘要，但不读取仓库外原始内容，也不替人判断访谈语义。

这比手工统计更可复算，同时避免为一周研究流程引入数据库或数据框架。明确重复意愿仍需由研究者依据原始回答标注，校验器只统计已标注且证据字段完整的记录。

### 5. 落地页采用可迁移的静态实现

新增独立 `landing/` 静态页面，使用语义化 HTML、少量原生 JavaScript 和 CSS 自定义属性，不初始化 Next.js。登记端点通过部署配置注入，源码中不得包含令牌；部署前未配置端点时页面展示不可提交的明确状态，避免假成功。

页面视觉在主题层映射 `design-tokens.json` 的浅色/深色语义 token，包括 `colorPrimary`、背景、文字、边框、状态色、圆角、间距、字号与阴影。业务选择器仅消费语义变量，不写裸色值或无 token 来源的尺寸；使用系统主题偏好切换深浅色，并保留可见焦点和减少动效偏好。

静态实现能最快验证文案和登记意向，也不会锁定第二周 Web 架构。替代方案 Next.js 会提前引入构建链和应用边界，第三方无代码落地页则难以把隐私、可访问性和版本记录纳入同一仓库，因此本周均不采用。

### 6. 以单一周验收摘要控制后续决策

`week-1-summary` 只从已校验的脱敏登记生成：有效访谈 8～10 次、独立合规样本至少 3 份、完整报告至少 3 份、明确重复意愿至少 3 人。摘要同时列出反面证据、样本限制和三个决策之一：继续第二周、补充验证、重新评估定位。

落地页登记数和一般兴趣只作为漏斗信息，不替代重复意愿门槛。这样避免用曝光或邮箱数量制造需求已验证的错觉。

## Risks / Trade-offs

- [人工脱敏遗漏敏感信息] → 使用接收清单和二次复核；原始文件不进仓库，未通过隐私门槛的批次保持阻塞。
- [受访者礼貌性表达被误判为承诺] → 只统计带明确时间条件和数据类型的再次提供意愿，一般兴趣单独记录。
- [三份样本差异过大导致分类不稳定] → 分类和字段契约版本化，保留“其他/不确定”，周末记录需要修订的边界而非强行统一。
- [透明公式在小样本下产生虚假精确感] → 报告同时展示原始计数、置信度和未测量项，允许有审计记录的人工调整。
- [外部表单端点不可用或造成数据泄露] → 仅收集最小信息、显式同意、无文件上传；上线前执行成功/失败路径测试，并允许替换端点。
- [静态落地页未来需要重写] → 将页面限定为独立获客入口和语义 token，第二周应用只需迁移文案与表单契约，不依赖其运行时。

## Migration Plan

1. 创建研究与分析模板、隐私边界和统一字段/分类版本。
2. 创建校验器及不含真实客户信息的合成样例，用自动测试覆盖通过与失败门槛。
3. 创建静态落地页、登记配置说明和可访问性检查。
4. 在受控位置开展访谈和接收样本，只把允许提交的脱敏证据与汇总带回仓库。
5. 运行校验并生成周验收摘要，再决定是否进入第二周。

回滚时可删除独立的 `landing/` 与 `validation/week-1/` 实现；它们不修改既有运行系统或数据。真实联系方式和原始样本按各自授权与保留期限在受控位置单独清理。
