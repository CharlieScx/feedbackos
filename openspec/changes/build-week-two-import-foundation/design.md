## Context

仓库当前只有协作规范、八周计划和第一周验证变更，没有应用代码、数据库迁移或运行环境。参见 `proposal.md` 的动机；本设计在不伪造第一周商业验证结果的前提下启动第二周工程工作，并为 `workspace-project-access`、`feedback-file-preview` 和 `import-batch-foundation` 三份行为规格提供实现路径。

这是一个跨 Web、API、数据库与对象存储的新系统初始化，涉及身份安全、租户隔离、文件处理和未来异步管道的数据边界。正式初始化前必须核验各依赖当前稳定版本并生成锁文件，不能从计划文档中的技术名称推断具体版本。

## Goals / Non-Goals

**Goals:**

- 用一次本地启动获得可工作的 Web、API、PostgreSQL 和 S3 兼容对象存储环境，并提供健康检查和迁移命令。
- 以 API 为业务与权限边界，交付注册登录、工作空间、项目、上传预览、字段映射和导入批次状态的纵向闭环。
- 让数据库记录、对象文件和预览状态可追溯且失败可恢复，为第三周质量管道留下稳定接缝。
- 从第一天建立 OpenAPI 契约、租户集成测试、三文件端到端测试、结构化日志和可复算的批次状态。
- 新页面从唯一主题入口消费设计 token，同时支持浅色与深色模式、键盘操作和明确的加载/错误状态。

**Non-Goals:**

- 不在本变更中开展或伪造用户访谈、真实客户样本、人工 Top 3 报告或付费验证。
- 不实现数据脱敏、精确/语义去重、Celery、Redis、Embedding、聚类、主题、优先级、版本对比或报告导出。
- 不实现邮箱验证、找回密码、团队邀请、细粒度角色、企业 SSO 或第三方登录。
- 不把映射已确认解释为数据已导入；第三周管道完成前不生成可分析的 `FeedbackItem`。
- 不为首版增加微服务拆分、消息总线、多智能体框架或生产云资源编排。

## Decisions

### 1. 按计划边界初始化单仓多应用

仓库采用 `apps/web`、`apps/api`、`packages/contracts` 和 `infra` 的最小结构。Web 使用 Next.js、React 和 TypeScript；API 使用 FastAPI、Pydantic、SQLAlchemy 与 Alembic；根目录提供统一的开发命令和 Compose 配置。实施第一项任务先从官方来源核验稳定版本，再固定 Node/Python 版本、包管理器版本与锁文件。

选择该结构是为了让 Web 与 API 可独立测试和部署，同时共享由 OpenAPI 生成的类型契约。替代方案是把所有逻辑放进 Next.js，但会偏离既定 Python 数据管道并让后续 Polars、Celery 与模型评测边界变模糊；现在建立更多服务或空包则没有行为价值。

### 2. 本地/CI 使用 Garage，测试/生产使用阿里云 OSS

第二周 Compose 只启动 PostgreSQL 和 Garage，Web 与 API 保持逻辑分离并可由统一开发命令运行。数据库和对象存储提供健康检查、命名卷与示例环境变量；Redis 与 Worker 留到第三周，在没有异步行为前不提前制造运行依赖。

应用只依赖自有 `StorageAdapter` 暴露的对象读写、删除和元数据操作，底层使用标准 S3 客户端。本地与 CI 指向 Garage，测试与生产首先指向阿里云 OSS；Endpoint、Region、凭据、bucket 与寻址方式全部由环境配置。OSS 仅支持虚拟托管请求且部分 ACL、ETag 与标准 S3 不完全相同，因此上线门禁必须在 OSS 专用 bucket 上覆盖实际使用的 API，不以 Garage 通过代替云端兼容验证。

选择 Garage 是因为它仍在维护、可用单容器启动，并能在无云账号和无公网条件下执行破坏性失败测试。MinIO 社区仓库和预编译分发已停止维护，不再作为新项目依赖；LocalStack 覆盖整个 AWS 模拟面且部分安全行为需额外启用，对当前只需对象存储的范围过重。替代方案是所有环境直接连接 OSS，但这会让本地开发和 CI 依赖云凭据、网络和计费，也增加误删共享测试数据的风险。

### 3. FastAPI 是业务与权限的唯一写入边界

Web 通过同源 `/api` 路径访问 FastAPI；开发环境由 Next.js 代理到 API，避免浏览器直接处理跨域凭据。API 发布 OpenAPI 文档，`packages/contracts` 由该文档生成 TypeScript 类型并在 CI 中检查是否漂移。页面不得直接连接数据库或对象存储。

替代方案是手写两份 TypeScript/Pydantic DTO，但重复定义容易让字段映射、状态枚举和错误码漂移。GraphQL 对当前资源规模没有额外收益。

### 4. 使用可撤销的不透明服务端会话

账号密码使用 Argon2id 哈希。登录后生成高熵随机会话密钥，只把密钥哈希和失效时间保存在数据库；浏览器通过 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie 持有原始密钥。修改请求同时校验同源 `Origin`，退出时撤销服务端会话。开发环境允许通过配置关闭 Cookie 的 `Secure` 属性，但生产默认不得关闭。

选择服务端会话便于退出撤销、后续成员权限变化和审计。自包含 JWT 会扩大密钥轮换与提前撤销问题；引入外部身份供应商会增加首版依赖并超出邮箱登录范围。

### 5. 所有资源查询从成员关系开始限定

核心关系为 `User -> Member -> Workspace -> Project`，资源标识符使用不可预测 ID。服务层不先按全局 ID 取资源再检查权限，而是从当前用户成员关系构造工作空间限定查询；跨租户资源统一返回不存在语义。数据库外键和唯一约束防止项目、数据源、批次与文件记录失去工作空间归属。

单靠前端隐藏入口不能提供隔离；数据库级 RLS 暂不作为唯一防线，因为迁移、后台 Worker 与本地测试还没有统一的数据库身份模型。第三周引入 Worker 时复用同一租户作用域服务，并再评估 RLS 作为纵深防御。

### 6. 上传采用 API 流式接收与同步有界预览

浏览器使用 multipart 上传并携带客户端生成的幂等键。API 将文件流写入受控临时文件，边写边计算 SHA-256 和大小；校验扩展名、签名与配置上限后，将对象写入按工作空间/项目分区的私有 bucket，再创建批次并生成预览。默认限制与预览行数作为配置公开给 Web，实施时以资源测试确定初始值，不散落在业务代码中。

第二周预览在请求内同步执行，因为输入有严格大小上限且交互需要即时结果。CSV 使用 Polars 并对声明支持的 UTF-8、UTF-8 BOM 与 GB18030 编码以及常见分隔符做受控检测；XLSX 使用 openpyxl 的只读模式读取第一个非空工作表。预览只保留表头、限定样本和安全解析元数据，临时文件在成功或失败后都清理。

替代方案是浏览器解析，但会产生前后端行为差异且无法建立可信服务端批次；第二周即引入预签名直传和异步 Worker 会扩大系统状态，而当前文件上限不需要它们。

### 7. 批次状态机先覆盖上传到映射确认

持久化实体包括 `User`、`Session`、`Workspace`、`Member`、`Project`、`DataSource`、`StoredFile`、`ImportBatch` 与空的 `FeedbackItem` 基础表。`ImportBatch` 保存状态、内容哈希、行数、预览元数据、版本化字段映射、幂等键和安全错误信息；状态只允许 `uploaded -> preview_ready -> mapping_confirmed`，任一步可进入 `failed`，合格失败可从同一对象重试预览。

文件对象写入成功但数据库事务失败时立即尝试补偿删除；补偿失败只记录对象标识与清理状态，不记录内容。映射确认只保存契约，不展开源行，也不创建 `FeedbackItem`。这避免第三周脱敏与去重规则尚未存在时，让原始反馈进入可分析表。

### 8. UI 使用单一 token 与明确的三步导入流

Web 建立统一 `ConfigProvider` 和主题模块，把权威 `design-tokens.json` 的 `lightToken`、`darkToken`、圆角、间距、字号与标题阶梯映射到 Ant Design token，并向 Tailwind 暴露语义 CSS 变量。业务页面只消费 Ant Design 主题、`useToken()` 或语义 Tailwind 类，不写硬编码色值和无来源尺寸。由于仓库尚无 UI，不存在需要兼容的旧品牌 token；后续若出现冲突，以权威 token 源统一主题入口。

页面流由认证页、工作空间/项目选择、项目导入页组成。导入页使用“上传文件 -> 检查预览 -> 映射字段”三步状态，始终显示当前批次状态、文件限制、预览截断提示和可恢复错误；表单标签、焦点顺序、键盘提交及状态提示满足基础可访问性。

### 9. 测试分层直接对应验收风险

API 单元测试覆盖邮箱规范化、密码与会话、文件检测、CSV/XLSX 解析、映射校验和状态转换；PostgreSQL/Garage 集成测试覆盖事务补偿、幂等重放和跨工作空间访问。测试环境另以专用 OSS bucket 运行存储契约测试，覆盖虚拟托管寻址、Put/Head/Get/Delete 和元数据行为。Web 组件测试覆盖表单和三步状态，Playwright 端到端测试使用三个无真实信息的合成文件执行“注册 -> 工作空间 -> 项目 -> 上传 -> 预览 -> 映射”。CI 还运行迁移、OpenAPI 契约漂移、类型检查、Lint、测试和生产构建。

测试不得使用真实客户材料。日志断言应证明原始反馈单元格、密码、Cookie 和存储凭据没有进入结构化输出。

## Risks / Trade-offs

- [访谈后置导致先开发后验证] → 限定为可复用的导入基础设施，保留第一周变更为未完成，不把工程验收解释为商业验证，并在后续计划中恢复真实访谈门槛。
- [同步解析在大文件下阻塞 API] → 配置严格大小/行数上限并使用流式写入、只读工作簿和有限预览；第三周再迁移到 Celery，不改变批次契约。
- [对象存储与数据库无法原子提交] → 先写私有对象、后提交批次，失败执行补偿删除并记录清理状态；集成测试覆盖每个失败点。
- [自建邮箱密码扩大安全责任] → 使用成熟密码哈希库、不透明会话、Cookie 与 Origin 防护、统一认证错误和密钥轮换配置；生产上线前补齐邮箱验证、找回与外部限流。
- [XLSX 多工作表语义不明确] → 第二周明确使用第一个非空工作表并在预览展示名称；真实样本证明有需要后再增加工作表选择。
- [设计 token 位于技能包而非运行仓库] → 初始化时建立项目主题映射模块并记录来源，业务代码只消费项目内语义 token；不让构建依赖开发者机器上的技能路径。
- [Garage 通过但 OSS 行为仍可能不同] → `StorageAdapter` 只使用两端共同支持的 API，并把 OSS 专用契约测试作为进入测试/生产环境的门禁。

## Migration Plan

1. 核验并记录稳定依赖版本，初始化目录、锁文件、环境变量示例和本地 Compose 服务。
2. 建立主题入口、API 健康检查和 OpenAPI 契约生成，确保空应用可启动与构建。
3. 通过 Alembic 一次性创建第二周核心表和约束，再实现身份、租户与项目 API。
4. 实现对象存储适配、上传/预览/映射 API 与状态机，随后接入 Web 三步流。
5. 使用三种合成文件运行完整检查并记录验收结果；第一周验证目录和变更保持不动。

本变更只有新增结构，没有线上数据迁移。回滚时停止新应用与本地服务、回退新增迁移并移除本变更创建的开发 bucket；不得删除第一周验证资产或仓库外研究数据。
